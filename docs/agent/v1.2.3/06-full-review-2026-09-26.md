## 1. 我对这个项目的完整认识

### 1.1 它是什么

**YanMusic 是一个基于 Electron 的桌面第三方音乐播放器**，以 GPL-3.0 发布，是 **EchoMusic**（作者 hoowhoami，参考版本 `2.3.1-beta.24`）的二次开发分支。它在保留上游 UI/功能的基础上，把播放内核**换成 libmpv**，并做了品牌化、一体化打包与一系列修复。

一句话概括其技术定位：**「四窗口 Electron 壳 + 进程内 libmpv 引擎 + 四个 Rust 原生 addon + 插件扩展体系」**。

### 1.3 关键设计决策（读代码后我确认的判断）

1. **libmpv 是「运行时 dlopen」而非编译期链接**：`mpv_ffi.rs` 用 `libloading` 动态加载，**零编译期依赖**——这是相对上游（需要 FFmpeg 开发库 + Windows 上 libclang）的实质优势，也是「Linux 无预装 mpv 时给清晰报错」的基础。
2. **播放引擎控制面高度集中且克制**：`controller.ts` 只把**固定白名单属性名**路由给 `mpv set_property`（约 8 个），不做泛化的 `setProperty` 透传。这牺牲了「8 个设置项无法下发」的灵活性（前序已记），但换来了**攻击面收敛**。这是一个有意的权衡，值得肯定。
3. **持久化是「Pinia 插件 + 原生 SQLite」双层**：`sqlitePersist` 钩住 `pinia.use()`，整 store 快照落 `pinia:setting` 等 KV 键。好处是统一，代价是**凭据随快照明文落盘**（见 H-3）。
4. **插件是「渲染层动态 import 的 JS」而非沙箱 VM**：`runtime.ts:2599` 用 `Blob` + `import()` 加载插件代码。这是**信任模型上的根本性选择**，几乎决定了后面所有插件相关风险的形态（见 H-2 / M-2 / M-6）。
5. **工程文化很强**：`.gitignore` 有解释性注释、`docs/release-process.md` 有三条硬纪律、`tests/` 有 20 个文件 131 例、CHANGELOG 逐条归因（「101 errors 由工具升级导致，非代码回归」）。**这个项目的自我审视密度远高于同类个人项目。**

## 2. 工程质量评价：先说好的部分

**这份报告若只讲漏洞，会失真。** 以下是我在审阅中确认为**真实优点**的地方，它们直接影响我对漏洞等级的判定（因为很多「漏洞」已经被缓解措施压低了实际风险）：

1. **IPC 层有统一收口且带观测**：所有 `ipcMain.handle/on` 都经 `ipcRegistry`，绝无散落的裸注册（`permissions.ts:279` 明确列出仅 9 个例外，且都列了名字）。这本身就是很强的可审计性。
2. **fail-closed 的安全策略函数**：`navigationPolicy.ts` 是纯函数、默认拒绝、只放行 `file:`/`about:`/dev 同源。这种「写成可单测的纯函数」的做法在个人项目里罕见。
3. **CSP 观测的工程细节惊人**：`cspReportOnly.ts` 记录了「meta 里的 Report-Only 会被 Chromium 完全忽略」「回传 file:// 原始头会导致 ERR_FAILED 白屏」「CSSOM 不受 style-src 约束」三条**实测结论**，并用测试固化。这是把「踩过的坑」变成「资产」。
4. **Rust 侧 null 检查与所有权处理是认真的**：`player.rs` 对每个 `mpv_get_property_string` 返回值都 `is_null()` 判断 + `mpv_free` 释放；`mpv_ffi.rs` 的 `transmute` 延长生命周期有明确注释说明「Library 不会在 Symbol 之前释放」。**未发现明显的 use-after-free 或双重释放**。
5. **SQLite 全部参数化**：`yan-storage/src/lib.rs` 1540 行中，所有用户数据都走 `?` 占位 + `params![]`，**未发现字符串拼接 SQL**。
6. **zip-slip 有第一方兜底**：`shared/archiveEntry.ts` 不信任第三方库的 `validateName`，自己再判一遍（且规则更严，额外拒 NUL）。**本次已实测**：10 个恶意名（含 `..`、绝对路径、盘符、NUL）全部被拒，5 个正常名全部放行。
7. **CN 的供应链加固**：14 处 `uses:` 全部固定到 40 位 commit SHA，并由测试持续校验。
8. **CI 权限按作业最小化**（**更正后新增**）：`build.yml` 在 `build`/`release` 作业仅授予 `contents: write`，两个通知作业仅 `contents: read`（详见 M-4 的撤回说明）。这是正确做法。
9. **fail-closed 的导航策略经实测确认为「真的 fail-closed」**：`navigationPolicy` 的 14 项纯逻辑断言全数通过，包括 `file:`/`about:`/dev 同源放行、其余一律拒。
10. **CSP 观测层「只观测、不强制」经实测确认**：不注入强制头、不做 last-modified、有去重计数、URL 有脱敏——这些自述的工程细节在运行中都成立。

**评价：这是一个「工程纪律明显高于其体量」的项目。** 下面所有漏洞，都应在这个前提下阅读——它们多数不是「粗心」，而是「架构选择带来的必然代价」或「尚未排期的技术债」。

### 3.0 分级标准

| 等级 | 定义 | 判定要点 |

#### 三级问题的双维度评定方法

三级问题的**排序**由两个维度合成，不是单一严重性：

- **D（修复难度）**：`D1` 局部单文件小改 / `D2` 需跨 2–3 文件或需重排格式 / `D3` 需重构或需要真机验证 / `D4` 需产品决策或外部条件

**呈递顺序 = 「低 D + 高 E」优先**（性价比最高：改起来快、用户能感觉到），「高 D + 低 E」排最后（改了用户也不知道）。每条的 `D/E` 已在条目上标注。

### 一级（High）

#### H-1　CI 工作流的脚本注入：任意 Issue 即可窃取 `GEMINI_API_KEY`

- **文件**：`.github/workflows/issue-ai-labeler.yml`（第 18–19 行与 `run:` 块）
- **触发**：`issues: [opened, edited]` —— **任何人发一个 Issue 就会执行**
- **证据**：

  ```yaml
  env:
    GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
    ISSUE_TITLE: ${{ github.event.issue.title }}     # ← 攻击者完全可控
    ISSUE_BODY: ${{ github.event.issue.body }}       # ← 攻击者完全可控
  run: |
    ...
    PROMPT="你是一个开源项目的 Issue 审核助手。...
    标题：$ISSUE_TITLE
    正文：$ISSUE_BODY"                                # ← 双引号内插值
  ```

- **为什么是漏洞**：GitHub Actions 会把 `${{ github.event.issue.body }}` **原样**放进 shell 脚本。Issue 正文由外部用户自由填写，其中若含 `"`＋`$(...)`（或换行后接命令），就能**闭合 `PROMPT=` 的双引号并注入任意 shell 命令**。而该步骤的 `env` 里正放着 `GEMINI_API_KEY`，且 runner 上一切皆可联网，直接 `curl` 外带即可。
- **影响**：**密钥泄露**（`GEMINI_API_KEY`，且 `API_URL` 指向第三方中转域 `runanytime.hxi.me`，一旦该中转被攻破或密钥泄露，影响进一步扩散）；runner 被用作跳板。
- **修复方向**：改为**不插值到 `run:`**，把不可信内容只经 `env:` 传入并加引号（`"$ISSUE_BODY"`），或用 `jq -n --arg` 组装（脚本后半段已经正确用了 `--arg prompt "$PROMPT"`，说明作者知道 `--arg` 的价值——**问题只出在 `PROMPT` 的构造方式**）。
- **判定**：**一级**。理由：利用门槛极低（发 Issue），后果明确（密钥外泄），且**当前无任何缓解**。
- **✅ 本地受控重放（已执行，非静态推断）**：我在本地 bash 中按该 workflow 的逐行语义重建了同一个 `run:` 脚本与同一套 `env`，用一个含 `"` + `$(...)` 的「Issue 正文」填入 `ISSUE_BODY`：

  ```bash
  # 与 workflow 同构：双引号插值
  PROMPT="…标题：$ISSUE_TITLE
  正文：$ISSUE_BODY"
  ```
  注入体（模拟攻击者 Issue 正文）：
  ```
  "; printf "[EXFIL] %s\n" "$GEMINI_API_KEY"; touch PWNED.txt; echo "x
  ```
  **实际输出**：
  ```
  [EXFIL] AIzaSyDUMMY_KEY_LOCAL_REPRO
  ```
  且 `PWNED.txt` 被成功创建（内容为 `attacker-filled-this`）。**结论：`PROMPT=` 的双引号可被闭合，注入的命令在写出前先拿到同步骤的 `GEMINI_API_KEY` 并成功外带。** 该重放不依赖任何假设——它执行的就是 workflow 里那段 shell。另需注意：同一 workflow 后半段已正确使用 `jq -n --arg prompt "$PROMPT"`，**漏洞只集中在 `PROMPT` 的构造方式**，修复面极小。
- **附注**：这是**我本次新发现**的问题，前序报告中未出现（前序只审了仓库代码与构建，未审 workflow 的注入面）。

#### H-2　插件以「主渲染进程内的动态 import」执行，等于完全可信代码

- **文件**：`src/renderer/plugins/runtime.ts:2591-2603`

  ```ts
  const importPluginModule = async (descriptor, code: string) => {
    const blob = new Blob([`${code}\n//# sourceURL=yan-plugin:${descriptor.id}`],
                         { type: 'text/javascript' });
    const url = URL.createObjectURL(blob);
    const module = (await import(/* @vite-ignore */ url)) as PluginModule;
    return { module, url };
  };
  ```

- **为什么是问题**：插件 JS **没有**在 Worker / iframe / `node:vm` 中执行，而是**直接在主渲染窗口的全局作用域里求值**。这意味着一个恶意插件可以直接：
  1. 读写 `window` 上的任何东西、劫持 `fetch`/`XMLHttpRequest`；
  2. **直接调用 preload 暴露的全部 `window.*` IPC 桥**（共 90+ 通道，见 H-3、M-2），包括 `storage:kv:get`、`plugins:fs:*`、`mpv:*`、`plugins:fs:get-file-url`；
  3. 读走 `pinia:user` 里的**登录令牌与设备指纹**（明文，见 H-3）。
- **当前缓解措施**（必须承认，这显著降低了「顺手就中招」的概率）：
  - `plugins:fs:*` 有 `hasPluginLocalFilesAccess(pluginId)` 门禁（要求插件启用 + 声明 `capabilities.localFiles` + 非安全模式）；

#### M-6　插件 SQL 黑名单可被注释分隔绕过：`VACUUM/**/INTO` 可向任意路径写文件

- **文件**：`src/main/pluginSqlite.ts` —— `BLOCKED_SQL_RE = /\b(?:ATTACH|DETACH)\b|\bVACUUM\s+INTO\b|\bload_extension\s*\(|\bPRAGMA\s+database_list\b/i`
- **为什么是漏洞**：该黑名单用 `\s` 匹配关键字之间的空白，但 **SQLite 允许用注释充当词间分隔符**。写成 `VACUUM/**/INTO '…'` 时，`VACUUM` 与 `INTO` 之间不再是 `\s`，正则不匹配 → **黑名单放过**，而 SQLite 正常解析执行。
- **✅ 已复现（真实 SQLite 3.53.1）**：

  | 载荷 | 黑名单是否拦截 | SQLite 是否执行 | 是否写出文件 |
  |---|---|---|---|
  | `VACUUM/**/INTO 'C:/any/path.sqlite'` | **False（漏过）** | **True** | **True（任意路径写出）** |
  | `PRAGMA/**/database_list` | **False（漏过）** | **True** | —（信息泄露：库路径） |
  | `ATTACH/**/DATABASE …` | — | **False** | —（SQLite 自身语法错，`ATTACH` 不能拆） |

  **结论：`VACUUM INTO` 可把插件数据库的完整副本写到进程有权限的任意路径**（对沙箱外目录亦然——路径由插件控制），属于「黑名单绕过 → 任意文件写」。`PRAGMA database_list` 则为路径信息泄露。
- **影响**：插件（含 H-2 场景下被投毒的插件）可借此把数据落到用户可预测的位置，或探测宿主路径。**注意：这与 H-2 是叠加关系，但即便不考虑 H-2，黑名单本身「号称拦截却可绕过」就是确定性缺陷。**
- **修复方向**：**放弃黑名单思路**（黑名单在 SQL 这种「注释/空白等价」的语言里天然不可靠）。改用 `sqlite3_set_authorizer`（或 rusqlite 的 `authorizer`）做**白名单式**语句/动作授权，只放行 `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`CREATE TABLE` 等插件必需动作，直接拒绝 `ATTACH`/`VACUUM`/`PRAGMA`/`load_extension` 等——**在解析层拦截，而非在文本层匹配**。
- **判定**：**二级**。理由：需要「能执行插件 SQL」这一前提（由插件体系提供，非本地任意进程），后果明确（任意路径写 + 信息泄露）。若考虑「黑名单被广泛依赖、一旦绕过即失守」，也可论证为一级——我保守地列二级，但**建议与 H-2 一并纳入插件隔离这一主线**。
- **附注**：本条为**本次新发现**，前序与本报告初稿均未包含；由你授予的运行时检测权限得以实证。
