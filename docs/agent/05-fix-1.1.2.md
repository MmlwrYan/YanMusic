### 1.1 修复前 / 修复后的精确代码位置与行为差异

**修复前**（`5ededad` 的父提交，`src/main/mpv/controller.ts:258-264`）：


**修复后**（当前工作树）：

## 2. P0：存量设置迁移未生效

### 2.1 先回答「`status=1` 的真实退出原因」

`docs/agent/logs/migration-verify-BEFORE-FIX.log`（原 `migration-verify.log`）里两次运行都是
`exit=1 / status=1 / signal=none`，隔离 userData 的 `logs/` 目录**完全为空**。原因**不是应用缺陷**：

> DSH harness 在 PATH 上的 `node` 是一个垫片
> `%APPDATA%\dsh-desktop\harness\.desktop-bin\node.cmd`，其内容会
> `set ELECTRON_RUN_AS_NODE=1`。该变量被 Node 派生的子进程继承后，**Electron 退化为
> 「run as node」模式**：`require('electron').app` 为 `undefined`，主进程在加载
> `dist-electron/main/index.js` 时抛
> `TypeError: Cannot read properties of undefined (reading 'setAppUserModelId')`
> 并**以 exit code 1 立即退出**。

因此在那些运行里：窗口没有创建 → 渲染层没有启动 → **渲染层里的迁移根本没有机会执行** →
`nativeAudioOptionsMigrationDone` 仍为 `undefined`。日志为空也与此一致（进程在 `initLogger()`
之前就死了）。

验证方式：改用 `Start-Process`（pwsh 环境里没有该变量）启动同一个隔离 userData，应用完整启动并
到达 `[Thumbar] setThumbarButtons result: true`；全新隔离 userData 中 `pinia:setting` 立刻出现
`demuxerReadaheadSecs=30, cache="yes", cachePauseWaitSecs=5, audioChannels="stereo",
nativeAudioOptionsMigrationDone=true`。

**结论：`status=1` 是验证环境（`ELECTRON_RUN_AS_NODE` 继承）造成的，不是迁移逻辑的问题。**
新增的 `scripts/verify-legacy-migration.cjs` 在 `spawn` 前显式 `delete env.ELECTRON_RUN_AS_NODE`，
并在报告里区分「脚本自己 `taskkill /T /F` 终止（Windows 上落定为 status=1、signal=null）」与
「应用自行退出」，从根上避免再次误判。

### 2.2 但确实存在一个真实缺陷：迁移跑得太晚

排掉环境因素后仍有缺陷 —— **只靠渲染层迁移，升级后的第一次启动不对齐**。

`src/main/app.ts` 的 `app.whenReady()` 回调：

```ts
119:  app.whenReady().then(async () => {
135:    const [, mpvInstance] = await Promise.all([
136:      initApiServer()...,
139:      initMpvPlayer(getMainWindow)...,
143:    ]);
146:    log.info('[Main] Pre-window initialization complete', ...);
162:    await createWindow();
```

即：**mpv 在 `createWindow()` 之前就已用「当时读到的设置」`initialize()` 完毕**，
而渲染层的迁移要等窗口挂载、`waitForSqlitePersistHydration()` 之后才跑。
所以升级后第一次启动，引擎拿到的是旧默认值 `1 / auto / 1 / auto-safe`，

**修复**：把迁移前移到主进程，在 `addon.initialize()` 之前完成并**落盘**。

| `src/main/mpv/audioOptions.ts` | `readNativeAudioOptions()` 先 `applyLegacyAudioOptionDefaultMigration(getPersistedRendererSettings())`，有补丁就 `getKvStorage().set(getStorePersistenceKey('setting'), migrated)`，并记录 before/after |

| `src/renderer/App.vue:200-202` | 在 `waitForSqlitePersistHydration()` 之后调用，作为安全网 |

## 3. P1：`audio-format` 期望 `auto` / 回读 `no` 的语义判定

### 3.1 判定：这是**映射层缺陷**，不是「正常归一化」

旧注释（`CHANGELOG.md` 与测试文件）写的是「实测确认 mpv 会把 `audio-format` 的 `auto`
规范化为 `no`（二者同义）」。**这个结论是错的**，三重独立证据如下。

### 3.2 证据一：libmpv 官方手册

mpv 官方手册 `DOCS/man/options.rst` 对 `--audio-format=<format>` 的说明是
「The values that `<format>` can adopt are listed below in the description of the
`format` audio filter.」—— 即只接受具体采样格式名，**取值表里没有 `auto`**。

### 3.3 证据二：引擎源码（与 `build/mpv/libmpv-2.dll` 同源，该 DLL 自报 `mpv v0.41.0-1012-ge8673660a`）

`options/m_option.c`：

```c
static int parse_afmt(void *opt, bstr param) {
    ...
    for (i = 1; i < AF_FORMAT_COUNT; i++)
        if (bstr_equals0(param, af_fmt_to_str(i))) fmt = i;
    if (!fmt) {
        mp_err(log, "Unknown format name: '%.*s'\n", BSTR_P(param));
        return M_OPT_INVALID;
    }
    ...
}

static char *print_afmt(void *opt, int fmt) {
    return fmt ? af_fmt_to_str(fmt) : "no";
}
```

`audio/format.c` 的 `af_fmt_to_str()` 只产出 `u8/s16/s32/s64/float/double/…p`，
**既没有 `auto` 也没有 `no`**。所以：`auto` → `M_OPT_INVALID`（写入被拒绝）；
「未设置」的内部值 `0` → 回读打印成 `"no"`。

### 3.4 证据三：可复现回读实验（命令 + 输出）


## 4. P2：`set_property` 的 `dead_code` 判定

### 4.1 判定：**重启生效**（启动期一次性下发），不是运行时生效

这 12 项音频/缓存选项在 `mpv_initialize` **之前**用 `mpv_set_option_string` 一次性下发，
运行期不存在任何改写通道。因此**不需要**为它们补运行时 `set_property` 白名单。

### 4.2 证据

1. **代码位置**：`native/yan-mpv-player/src/player.rs` 的「设置初始化选项（必须在
   `mpv_initialize` 之前）」段落里，全部 12 项 `set_option(...)` 都排在
   `mpv_initialize(...)` 之前。libmpv 的 `mpv_set_option_*` 在 initialize 之后即不可用，
   必须改用 `mpv_set_property_*` —— 而代码里没有这条路径。
2. **导出面**：`lib.rs` 的 31 个 `#[napi]` 导出中没有任何能改写这 12 项的入口。
   唯一的通用逃生口 `MpvPlayer::set_property` **未导出**，这正是重建日志里
   `warning: associated items \`new\` and \`set_property\` are never used`
   （`native/yan-mpv-player/src/player.rs:127`、`player.rs:945`）的来源 ——
   **该警告本身就是「没有运行期入口」的编译期证据**。
3. **调用链**：`MpvController.command('set_property', …)` 的白名单只路由 8 个固定属性
   （`force-media-title / audio-exclusive / audio-device / pause / volume / speed / aid / af`），
   不含这 12 项，所以运行期改设置不会到达 mpv。

### 4.3 测试中的显式断言

`tests/native-engine-options.test.ts` 的 P2 用例：

- 断言 `Object.keys(addon)` 中**不存在** `setProperty` / `set_property` / `setOption` /
  `set_option`，也不存在这 12 项各自的运行期 setter；
- 断言初始化时下发的值立即生效；
- 断言**重建**（等价于重启应用：主进程重新调用 `addon.initialize`）后新值生效
  （`cache-secs 30 → 77`、`cache yes → no`、`audio-channels stereo → mono`、
  `demuxer-readahead-secs 30 → 11`、`audio-buffer 0.5 → 1.5`、`cache-pause yes → no`、
  `cache-pause-wait 5 → 2.5`、`audio-samplerate 0 → 48000`、`gapless-audio weak → no`）。

对应 UI 行为：**改这些设置后必须重启应用才生效**（已在 `CHANGELOG.md` 与设置页说明中写明）。

`scripts/verify-legacy-migration.cjs` 已把这两种情况在输出里分开表述。
